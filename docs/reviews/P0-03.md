# P0-03 — Service credentials, audit and safe logging

Status: implemented, verified, and approved by the user. P0-01 and P0-02 approved.

## Delivered

- Separate runtime and maintainer API processes and route groups. The runtime
  has no admin routes; the maintainer service has no student account routes.
- Distinct, non-superuser database logins with no role memberships, schema DDL,
  temporary-table, create-role or RLS-bypass privileges. Startup rejects the
  wrong DB username; readiness verifies role name and privilege flags.
- One-shot local role bootstrap and separate migration job. Neither API receives
  owner/migrator or the other API's credentials. Running-container configuration
  inspection verified this without displaying secret values.
- Protected global release, skill, chunk and demonstration tables. Runtime has
  no base-table/draft access and can SELECT only published security-barrier views.
  Maintainer can maintain global tables but cannot read student account tables.
- Append-only audit records for versioned API requests. Runtime can append but
  cannot read/update/delete/truncate history; maintainer can read/append only.
  An UPDATE/DELETE trigger also rejects row-history changes by the table owner.
- Typed JSON application logs contain only request UUID, service, bounded action,
  route template, HTTP status and outcome. Raw URLs, account IDs, query strings,
  tokens, student content, exception strings and actor UIDs are excluded from logs.
  Third-party/unstructured logging is disabled in the API process.
- Generic errors on unexpected request failures. If audit persistence fails,
  otherwise-successful responses return 503; authorization denials stay denied.
- Maintainer-only **View recent activity** UI and `/v1/admin/audit`, returning
  bounded operational metadata without actor UIDs or request content.

## Migration and operational impact

Alembic `0002_service_boundaries` adds `global_knowledge`, `published_knowledge`,
minimal protected tables/views, audit_events and the append-only trigger, and
explicit grants. Full release/document/domain contracts are extended in P0-04.
The local bootstrap transfers existing identity tables to the migrator and
preserves data; it can be rerun for existing volumes. New objects get no implicit
runtime/admin access. New migrator-created functions revoke PUBLIC execution by
default. Example service passwords are local fixtures only.

Audit writes occur after the current request transaction. The only existing
mutation is idempotent account provisioning: an audit failure can leave that
account provisioned while returning 503. Future release/data mutations must put
business changes and their audit event in one transaction. Audit retention and
privileged maintenance are handled at later privacy/operations gates.
