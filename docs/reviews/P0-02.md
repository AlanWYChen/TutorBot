# P0-02 — Authentication and student isolation review

Status: implemented and approved by the user. P0-01 approved by the user.

## Delivered

Firebase email/password sign-in and sign-out, with in-memory browser sessions.
The API verifies ID tokens through the Firebase Admin SDK with revocation enabled,
validates timestamps explicitly, and compares token roles with privileged current
custom claims. Missing roles default to student; unknown/stale roles are denied.
No application endpoint grants or changes maintainer privileges.

Production startup rejects emulator configuration. Local/test emulator mode
requires a demo project. The local CLI provisions two synthetic students and one
synthetic maintainer, guarded against execution outside the local demo emulator.

Student account provisioning and reads persist in PostgreSQL. Repository scope
is bound to verified identity; account IDs are resource selectors only. Cross-student
reads return the same 404 as nonexistent IDs. Admin routes require admin; student
routes require student. Fixed same-origin web proxy routes forward only bearer
credentials, never identity/role headers or query parameters.

Changed paths: `apps/api/app/auth/`, `apps/api/app/students/`, `apps/api/app/db.py`,
API config/main, `apps/api/migrations/`, `apps/api/alembic.ini`, API tests and
`apps/api/scripts/seed_local_auth.py`; `apps/web/components/sign-in.tsx`,
`apps/web/lib/firebase.ts`, fixed proxy/public configuration routes, proxy tests
and landing page; dependency locks, Docker/Compose, Makefile, CI, README,
ADR 0002 and playbook tracker.

## Verification

- Web lint, TypeScript and six Vitest tests passed.
- API lint and strict type checks passed.
- Twelve API unit/SDK tests passed. Four integration tests are intentionally
  skipped in the isolated unit run and pass separately with real services.
- Four real PostgreSQL/Firebase integration tests passed: tenant ownership,
  RBAC, invalid/expired/wrong-project/wrong-issuer/stale-role tokens, disabled
  users, removed maintainer privileges, revoked tokens, idempotent provisioning.
- Migration test passed in a disposable database: upgrade, FK/role constraints,
  downgrade, upgrade again. The application database is not rolled back.
- Production-mode SDK verification exercised offline with synthetic RSA keys:
  valid signatures accepted; unsigned, incorrectly signed, expired and wrong
  project/issuer tokens rejected.
- Browser verified failed sign-in, student sign-in, sign-out, maintainer sign-in.
  Screenshots: `P0-02-student.png`, `P0-02-sign-in.png`.
- Production web build, seven-service startup and live smoke checks passed.
- Production npm audit: zero advisories. The five existing lint-tool development
  advisories remain as documented in P0-01.

The emulator initially accepted an expired token because its SDK path skips
cryptographic/time validation. Explicit application timestamp validation fixed
that regression; the real SDK signature path is tested separately. Firebase's
unsigned local emulator tokens are still intentionally forgeable development
fixtures, so emulator access is not a production security guarantee.

## Migration impact and limitations

Alembic revision `0001_identity` introduces `users` (unique Firebase UID, role
constraint) and `student_accounts` (unique user FK). Compose applies pending
migrations before serving requests. P0-04 adds the remaining domain schema.

The Firebase client SDK requires Node 24.12+; images and CI now pin 24.12.0.
A patched gRPC transitive dependency is locked through an npm override.
API tests still emit the existing Starlette/httpx deprecation warning.

DB service privileges, global knowledge write restrictions, audit events and
safe logging are the next ticket. PDF/profile/session isolation will extend
these ownership predicates as those resources are introduced. No real student
records, uploads, global teaching tools or provider calls were added. Real
Firebase staging verification remains part of the deployment gate.
